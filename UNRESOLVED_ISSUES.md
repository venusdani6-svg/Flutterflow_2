6. **A SECOND `page.ensureActions(...)` edit to an itemBuilder-scoped trigger that a PRIOR push already successfully applied can silently no-op** (PROJECT_KNOWLEDGE.md §113), even when the pushed content genuinely differs. Note: a FIRST `ensureActions` application to a given trigger is unaffected — confirmed working correctly 18+ times across §112/§114/§115/§116/§117. Full writeup in `.cursor/rules/project_rules.md`. Root cause not conclusively isolated.
7. **`ensureReplaced` cannot substitute for a blocked `ensureActions` re-edit when the target widget needs `ItemRef()`** (PROJECT_KNOWLEDGE.md §118) — `ItemRef()` only resolves inside a real `itemBuilder` closure; `ensureReplaced` constructs a brand-new widget definition, the same category as `ensureInsertedAfter`/`ensureInsertedBefore`, which already can't supply it either. This is what finally closed off item 8 in "Recently closed" above.
8. **A parameterized `app.actionBlock` (one with `params:`) failed to compile** (`Custom action argument "X" is not set properly`) on its first-ever use in this project (§117, WorkPostDetailPage). Every zero-param action block in this rollout works fine; only the one parameterized attempt failed. Root cause not isolated — worked around by calling the underlying custom action directly inline instead.
9. **Any two structural mutations (`ensureInsertedAfter`/`Before`/`Replaced`) sharing the same target key across separate pushes is unsafe** (pre-existing, `.cursor/rules/project_rules.md` "GENERALIZED LESSON") — confirmed hit and avoided again in §119 (a new insertion's natural anchor already had an active insertion from an earlier session). Always grep the whole file for a candidate anchor key before adding a new structural mutation to it.
10. **`ensureInsertedAfter`/`ensureInsertedBefore` self-heal ONLY by exact relative position, not by widget name across the whole tree** (PROJECT_KNOWLEDGE.md §120) — switching which side of the same anchor a named insertion targets (e.g. `ensureInsertedAfter` → `ensureInsertedBefore` to fix ordering) does not relocate the original widget; it creates a genuine second, independent copy and leaves the stale one live. Caught this session only by reading `generated_code/`'s compiler-assigned disambiguation suffixes after a push that reported clean success. Any future reposition of an already-inserted widget must pair the new insertion with an explicit `page.ensureRemoved(page.findByKey(<stale-key>))` in the same push — never assume the self-heal covers a changed side/anchor. Distinct from item 9 above (that one is two independent calls sharing one anchor; this one is a single logical widget's insertion mode changing across pushes).
11. **Documentation reconciliation debt**: `IMPLEMENTATION_PLAN.md`'s requirements catalog has recurring stale tags not reconciled against later phase completions (e.g. §3.5.9's message-history filters tagged `[MISSING]` despite Phase 6 stating it was built; §121/§122/§124 found a 3rd through 7th occurrence this session alone — group-invite acceptance's own item was tagged `[MISSING]` for 2 of its 3 sub-parts, sent-request-history/reservation-history-filter/notification-settings/phone-self-service/debt-history were ALL tagged `[MISSING]` despite earlier sessions already covering them). Worth a dedicated pass so the catalog can be trusted at face value again.
12. **A widget with a `network_only`-style access-scoping need has no dedicated design pattern in this codebase yet** — §121's affiliate-network recruitment path improvised private visibility on the shared public `work_posts` collection via 2 new fields + in-memory filtering in every read path, rather than a separate collection. Worked correctly and cleanly this time (small dataset, few read paths), but is a one-off, not an established convention — a future feature needing the same "same shape, restricted audience" pattern should re-evaluate rather than assume this is "the way," and this codebase's own `firestore.rules`/index strategy has no opinion on it either way yet.
13. **A `dsl/edit.dart` trigger button can accumulate 2-3 superseded `ensureActions` declarations for the SAME key across sessions, with only the LAST one in file order actually live** (PROJECT_KNOWLEDGE.md §121/§123, both hit this on non-itemBuilder buttons: `ReservationDetail`'s ApproveButton and `PaymentConfirm`'s/`ExtensionPayment`'s submit buttons) — always grep for every `page.findByKey('<key>')` occurrence and edit the LAST (highest line number) one, never assume the first/only-uncommented match found is the live one.
14. **CocomisePage's 7 genre-filter chips are hardcoded native widgets, not synced to the admin-editable `cocoten_genres` master list** (PROJECT_KNOWLEDGE.md §125, `adminGetCocotenGenres`'s own comment, admin.ts) — an earlier session explicitly flagged this exact block as "too fragile to touch outside a dedicated pass" and this session respected that rather than re-litigating it inside an already-large batch. Genre filtering itself still fully works today; it just can't reflect an admin adding/removing a genre beyond the original 7.
15. **A block explicitly flagged as too risky to re-run (e.g. `ensureReplaced` targeted by `findByName`) may still be safely re-doable if the SPECIFIC mechanism causing the risk can be swapped out** (PROJECT_KNOWLEDGE.md §125) — a frozen CocomisePage grid rebuild was avoided for a session because `findByName` re-resolution after a replace was "untested... not worth risking." Re-reading the CURRENT live key from the freshly-regenerated typed SDK and targeting via `findByKey` instead (the same proven-reliable mechanism used everywhere else in this project) safely unblocked it. Before treating a disclosed risk as a permanent wall, check whether the risk is about the SPECIFIC selector/mechanism used, not the operation itself.
16. **A shared helper function's own call sites can already carry the exact signal a new feature needs, avoiding any call-site changes at all** (PROJECT_KNOWLEDGE.md §126) — before adding a new parameter (or classifying call sites by hand), grep what the existing call sites already pass; `sendPushNotification`'s notification-preference enforcement needed zero call-site edits because every one already tagged its payload with a `type` field for an unrelated original purpose (client-side notification routing) that happened to map 1:1 onto the new feature's own categories.
