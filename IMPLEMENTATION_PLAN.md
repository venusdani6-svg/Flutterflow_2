**Reservation status machine — build exactly this seven-state sequence, each transition trigger explicit:**

| # | Status (JP) | Entry trigger |
|---|---|---|
| 1 | リクエスト中 | Guest submits request; Stripe Authorize succeeds → `requires_capture` |
| 2 | 確定決済済 | Cast taps approve |
| 3 | 合流待ち | Automatic, on reservation start time reached |
| 4 | 交流中 | Both guest and cast tap "meetup confirmed" |
| 5 | 完了報告待ち | Reservation end time reached, OR cast's completion report |
| 6 | 評価待ち | Cast completion report triggers Capture; transition fires on the Stripe webhook success event, not optimistically on button tap |
| 7 | 完了 | Guest posts a review, OR 24h auto-batch closes it |

`[MISSING]` in full — `reservation_detail.dart`'s approve/decline/meetup/complete/rate/cancel buttons are all unwired; no Cloud Function implements any transition.

2. **30-minute rule** (server-time based): if the same guest↔cast pair's previous Capture happened ≤1800s ago, generate the new reservation's taxi fee as ¥0, and persist a duplicate-prevention flag so it can't be double-relaxed. `pair_history.pair_key` (guestId+castId) and `last_capture_at` exist in the schema for exactly this. `[MISSING]`.

## 4. Spec-internal tensions — RESOLVED 2026-08-10

These five points were flagged as genuine contradictions or gaps across the client's own source documents, rather than silently resolved one way — that discipline is preserved below for traceability. **All five have since been confirmed directly and are now decided**, each landing on this plan's original recommendation; nothing here changes any other section of the plan, it just removes the "confirm before Phase X" gate that previously blocked those phases.

**4.1 — KYC method: DECIDED — manual review now, Stripe Identity later.** `アプリ仕様書` §① and `Stripe決済スキーム仕様書` §① both specify Stripe Identity with automated webhook-driven `is_verified` flipping. But the negotiated MVP scope explicitly downgrades this to manual document upload + manual admin approval, with Stripe Identity deferred to phase 2 ("初期は「管理画面で手動確認」（AI自動照合は高コスト）" / "Stripe Identityは二次開発で段階導入"). **Confirmed 2026-08-10**: build manual upload + admin review for Phase 2 as the MVP-tier deliverable, and design the `users.kyc_status`/`is_verified` fields so a later Stripe Identity webhook can flip the same fields without a schema migration — i.e., build the data model for both paths now, build only the manual UI now, wire the Stripe Identity webhook path in as a phase-2 slice (§8 Phase 12b).

**4.2 — Affiliate reward settlement timing: DECIDED — accrue at Capture, pay out monthly on the 5th.** Instant-on-Capture (Stripe scheme doc — "売上確定（Capture）成功と同時に...アフィリエイト報酬を送金する," a literal, immediate Transfer instruction, using the same 送金する/"remit" verb the same document uses elsewhere for an actual Stripe Transfer call) vs. monthly-batch-on-the-5th gated by a 3-day activity rule (Affiliate doc, reaffirmed by the client's own confirmed Q&A) — these cannot both be literally true, so this was a genuine contradiction, not just a difference of detail. **Confirmed 2026-08-10**: Capture success creates the *ledger accrual event* (a `pending`-status `affiliate_rewards` row, per §3.9.13's Phase-1/Phase-2 pattern applied to affiliate rewards too) — but the actual Stripe **Transfer execution** only happens in the monthly batch job on the 5th, after confirming the referrer hit ≥3 active days, both parties remained `approved` throughout (§3.7.12's mutual-approval rule), and neither party left before the payment date. This reading privileges the Affiliate document's timing and safety gates over the Stripe document's literal "transfer at Capture" instruction, because that document's own stated rationale (ghost-member and quit-and-run prevention, §3.7.12) directly argues for a delayed, gated settlement — and it matches the client's explicitly confirmed answer #4 in the 2026-02-21 Q&A ("翌月5日にシステムが判定...条件クリアしたアフィリエイターへ、システムが自動で資金移動") as well as the identical resolution the sister project's client independently confirmed for this exact question (§6, defect #12).

## 5. Data model remediation plan (Phase 1 of §8, detailed here because it gates everything else)

All of this happens through `dsl/edit.dart` using the SDK's schema helpers, then `flutterflow ai run` — never by hand-editing `generated_code/`.

Since Phase 5 adapts that backend rather than writing a new one, **this project's schema must converge on the backend's real names, not the other way around** — renaming the backend to match a schema guess would just re-break the working parts of it. The items below fold this correction in.

1. **Fix the two known field-name typos**: `reservations.res_ic` → `res_id`; `extension_payments.reservationld` → `reservationId`, `extension_payments.userld` → `userId`.
