3. If a NEW FlutterFlow AI SDK/tooling gotcha is discovered (not specific to this project's own business logic — a DSL quirk, a codegen quirk, a CLI behavior), add it to `.cursor/rules/project_rules.md`'s "FlutterFlow quirks learned the hard way" section instead of (or in addition to) here, so it's visible in the pre-task ritual even for someone skimming only the rules file.

**Real SDK-surface findings worth keeping, both discovered by hitting real `compileDslApp` failures, not by reading docs alone:**
- **Raw-added custom actions (`addCustomAction` inside `app.raw`) are invisible to a page built via `app.ensurePage` in the SAME script run** — `compileDslApp` failed with `No custom action named "..." found in the project` even though the action and the page were both declared, correctly, in the same push. Declarative pages are compiled before `app.raw`-queued mutations are applied, so a raw-declared action doesn't exist yet when the page's own `CallCustomAction.named(...)` reference is validated. **Fix: use the declarative `app.customAction(...)` instead** (not the brownfield `addCustomAction`) — it runs in the same declarative pass as pages. Its own doc comment confirms an identical rerun is a no-op (only a changed payload throws), so it's safe enough to use in an edit flow for a case like this, despite the general brownfield guidance elsewhere preferring `find*`/`add*`. Still commented out post-landing per this project's standard one-shot discipline.
- **`app.editPage(...)` requires the typed `ff.Pages.*` handle for its own page argument once ANY page in the project has been touched by this workspace's DSL at all — a raw string page name is rejected outright**, `Use ff.Pages.signupPage instead of a raw page name in editPage("SignupPage")`. Same rule applies to `WidgetState(...)`'s first argument when referencing a PRE-EXISTING native widget (not one freshly inserted in the same push) — `Use ff.Pages.phoneVarification.widgets.byKey(...).single instead of WidgetState("MobileNnmberField")`. Notably this did NOT apply to `Navigate(...)`'s own page-target argument (confirmed via `_resolvePageName`'s own source: a bare string is a fully sanctioned, separate code path there) — only `editPage`'s own top-level selector and `WidgetState`'s widget-reference argument are gated this way. Also did not apply to a widget inserted fresh in the SAME push (`SmsCodeField`, via `ensureReplaced`) — consistent with the already-known "a same-run-inserted widget has no typed handle yet" rule; a raw string is the *correct* choice there, not a workaround.
- **Retargeting a `Navigate` action buried inside an existing native multi-step chain, without touching anything else in that chain**, is a real, generalizable pattern: `page.mutateNode(selection, (node) { ...walk node.triggerActions.first.rootAction... })`, recursing through `followUpAction` AND `conditionActions`' true/false branches (a linear walk alone would miss anything nested in a conditional), looking for `node.action.hasNavigate() && node.action.navigate.pageNodeKeyRef.key == oldTargetKey` and reassigning just that one field. Replaced with one real `TextField` (`Keyboard.number`) — a disclosed, function-over-form trade-off, not an oversight.
